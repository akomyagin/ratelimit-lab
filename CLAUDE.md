# CLAUDE.md

Инструкции для AI-сессий (Claude Code) в репозитории `ratelimit-lab`. Эти
инструкции имеют приоритет над поведением по умолчанию — следуй им точно.

## Что это за репозиторий

`ratelimit-lab` — учебная **библиотека rate limiting на Go** плюс бенчмарк-сьют.
Три single-process алгоритма (token bucket, sliding window, leaky bucket) + две
lock-free CAS-реализации token bucket, сравнение throughput/latency под
конкурентной нагрузкой. Соло pet-проект с приоритетом **обучения Go и конкурентности**;
реализация ведётся AI-ассистентом. Не бизнес — экономическая целесообразность,
монетизация и дистрибуция не оцениваются. Бюджет ≈ **$0** (чистая библиотека, без
инфраструктуры и сети). Никакого distributed-варианта в MVP — только single-process.

Полное видение — [`docs/PLAN.md`](docs/PLAN.md); технический план и разбивка по
Этапам — [`docs/TECHNICAL_PLAN.md`](docs/TECHNICAL_PLAN.md); за пределами MVP —
[`docs/POST_MVP_PLAN.md`](docs/POST_MVP_PLAN.md).

## Структура репозитория

Текущее состояние (Этапы 0–6): реализованы `limiter.go` (порт
`Limiter` + `Clock` + `SinceClock` + `SystemClock` + `admitEpsilon`),
`tokenbucket.go`, `slidingwindow.go`, `leakybucket.go`,
`lockfree_tokenbucket.go` и `atomic_tokenbucket.go` — все с тестами. Заглушек
больше нет: Этап 5 заменил `cmd/bench/main.go` рабочим харнессом (плюс
`runner.go`/`report.go` в том же `package main`) и добавил микробенчмарки
`internal/limiter/limiter_bench_test.go`.

**Lock-free реализаций две, и это не версии одного и того же**, а вместе с
mutex-версией три точки сравнения: «наивный CAS» и «CAS с продуманной
раскладкой». Знать до чтения кода:

- `LockFreeTokenBucket` (Этап 4) — CAS по `atomic.Pointer` на неизменяемый
  снапшот `{tokens, last}`. Проигрывает mutex примерно втрое, и **это
  задокументированный результат, а не недоделка**: реализация остаётся
  контрольной точкой и не оптимизируется. Побочный эффект «деная без CAS»:
  дрейф float64 здесь структурно не копится, поэтому `admitEpsilon` закреплён
  отдельным unit-тестом на чистую функцию, а не сценарным тестом, как у соседей.
- `AtomicTokenBucket` (Этап 6) — CAS по одному `atomic.Int64`. Хранит **время,
  а не токены** (момент, в который запас равен нулю), вся арифметика горячего
  пути целочисленная, эпсилон не нужен и добавлять его нельзя. Обгоняет mutex
  под конкуренцией за счёт четырёх измеренных приёмов: одно слово состояния;
  часы читаются один раз **до** петли и не перечитываются на ретрае; все
  константные поля вынесены в локальные переменные **до** петли; падинг
  **128 байт** между целью CAS и read-only полями (64 измеренно хуже — парный
  префетч линий). Падинг закреплён тестом на `unsafe.Offsetof` — это часть
  дизайна, а не мусор в структуре. Ценой идёт квантование rate: период хранится
  целыми наносекундами, конструктор паникует на нерепрезентуемых параметрах.

Отказ **без CAS** — общее сознательное расхождение обеих lock-free версий с
mutex-версией, которая персистит refill и на отказе. Обоснования — в
doc-комментариях обоих файлов; разборы — в
`docs/plans/stage-4-lockfree-tokenbucket.md`,
`docs/plans/stage-6-fast-lockfree.md` и `docs/RESEARCH.md` (§1.3–§1.5, §2.1).

Прогресс по этапам держится здесь, а не в `TECHNICAL_PLAN.md`: тот описывает,
*что* делать в каждом Этапе, и заголовки разделов не помечаются как
завершённые. Сверяться при сомнении — с `git log` и содержимым
`internal/limiter/`.

## Ключевые архитектурные решения (не переоткрывай без причины)

- **Один порт `Limiter`** (`Allow() bool` / `AllowN(n int) bool`) — за ним все
  алгоритмы; каждый — отдельный файл. Инвариант: **все реализации безопасны для
  конкурентного использования из множества горутин** (SKILL §2).
- **Абстракция `Clock`** — время инжектится, тесты корректности детерминированны
  через fake-clock, без `time.Sleep` (SKILL §3, `TECHNICAL_PLAN.md §4`). Сам порт
  `Clock` (`Now() time.Time`) **не меняется**; `SinceClock` добавлен рядом как
  опциональное расширение (`Since(t) time.Duration` — только монотонные часы,
  ~вдвое дешевле `Now`). Реализация проверяет его type assertion'ом **один раз в
  конструкторе** и деградирует к `Now()`; `fakeClock` намеренно оставлен
  `Now`-only, чтобы путь деградации оставался покрытым.
- **Lock-free token bucket — центральная точка проекта**, а не «ещё вариант».
  CAS-цикл на `sync/atomic`; под него — отдельный stress-тест на гонки и
  обязательный `-race` (SKILL §5).
- **`admitEpsilon` — относительный** (`limit * 1e-9`), а не абсолютная
  константа: абсолютная вырождалась в no-op при лимитах от 2^24 (ULP там
  3.7e-9). Масштаб — тот операнд, с которым сравнивают: `n` у спендящих,
  `capacity`/`limit` у наполняемых. На `AllowN(1)` умножение на 1.0 точное,
  поэтому вердикты всех прежних путей бит-в-бит те же. В `AtomicTokenBucket`
  эпсилон не используется вовсе — там нечего компенсировать.
  Потолок 2^24 снят **только на наполняемой стороне** (`SlidingWindow`,
  `LeakyBucket`): там эпсилон прибавляется к тому же операнду, по которому
  масштабируется. На спендящей стороне (`TokenBucket`,
  `LockFreeTokenBucket`) эпсилон прибавляется к накопленному `tokens`, а
  масштабируется по `n` батча — при большой `capacity` и малом `n` (например
  `NewTokenBucket(1, 1<<25, clk)` с `n=1`) прежняя граница 2^24 остаётся.
  Это известное ограничение, не недоделка: масштабировать по
  `max(n, capacity)` отвергнуто — при `capacity = 1<<30` слак стал бы 1.07
  токена, то есть наблюдаемым, что хуже исходной проблемы. Полноценное
  решение — хранить время вместо токенов, как в `AtomicTokenBucket`, где
  эпсилон не нужен вовсе.
- **Только стандартная библиотека.** Внешние модули не добавляем без веской
  причины — учебная цель в том, чтобы понять примитивы, а не собрать зависимости.
- **Заглушки Этапа 0 помечены `TODO(Этап N)`** — при реализации заменяем
  содержимое файла, не плодим параллельные `*_v2.go`. На Этапе 5 последняя
  заглушка снята; правило остаётся на будущие этапы. Осознанное исключение —
  Этап 6: `atomic_tokenbucket.go` не версия `lockfree_tokenbucket.go`, а третья
  точка сравнения, поэтому лежит рядом, а не вместо.
- **Бенчмарки меряют только путь допуска, и это осознанно.** `rate`/`capacity`
  по умолчанию заведомо выше нагрузки, потому что на непустом бакете сравнение
  mutex против CAS осмысленно, а на пустом — нет: lock-free возвращает `false`
  без CAS и без аллокации, mutex-версии и на отказе берут блокировку. Разрыв
  измерим: `go run ./cmd/bench -rate=1000 -capacity=1` даёт lock-free ~27×
  «преимущества», целиком созданного дешёвым путём отказа. Поэтому `cmd/bench`
  печатает warning-строку, как только в любой строке `denied > 0` — цифры там
  сравнивать нельзя. Не «чинить» это подкруткой конфигурации.

## Команды

```bash
export PATH="$HOME/sdk/go/bin:$PATH"   # Go 1.23 в ~/sdk/go/bin
go build ./...
go vet ./...
go test ./...
go test -race ./...                    # ОБЯЗАТЕЛЬНО перед коммитом кода этапов 1+
go test -bench=. -benchmem ./internal/limiter/   # микробенчмарки (-benchmem обязателен: allocs/op — результат Этапа 5)
go run ./cmd/bench                              # сравнительная таблица по всем 5 алгоритмам, ~10с
go run ./cmd/bench -format=markdown             # та же таблица готовой GFM-таблицей для README
go run ./cmd/bench -percentiles                 # + p50/p99/p99.9 (ценой per-call time.Now())
```

Перед коммитом кода: `go build ./... && go vet ./... && go test -race ./...`
должны проходить чисто.

## Dev-workflow

**Разбивку на шаги и выбор моделей задаёт глобальный `~/.claude/CLAUDE.md`
(раздел «Пайплайн кодинга») — здесь они сознательно не дублируются.** Раньше
дублировались и разошлись: проектный файл предписывал основную сессию на Sonnet,
глобальный — на Opus, и следующая сессия получала два взаимоисключающих
предписания. Один источник правды — глобальный файл; ниже только то, что
специфично для `ratelimit-lab`.

Git-workflow: главная ветка — **`master`**; **новая ветка от `master` на каждый
Этап → PR → merge**. Коммить/пуш только когда этап завершён (или пользователь
явно попросил). Conventional-commit с **русским subject**; завершай commit-
сообщения трейлером `Co-Authored-By: Claude`.

Проектный гейт перед коммитом кода — см. «Команды» выше. `-race` обязателен
начиная с Этапа 1: главный инвариант проекта — безопасность конкурентного
использования, и без прогона под детектором гонок он не проверяется.

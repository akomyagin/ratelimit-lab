# ratelimit-lab

Учебная **библиотека rate limiting на Go** с честным бенчмарк-сьютом. Три
классических алгоритма ограничения частоты для одного процесса — **token
bucket**, **sliding window**, **leaky bucket** — плюс **lock-free** (CAS-based)
вариант token bucket, и сравнение их throughput/latency под конкурентной
нагрузкой.

Это соло pet-проект с приоритетом **обучения**: конкурентные примитивы
(atomic vs mutex vs lock-free CAS-циклы) и алгоритмическая корректность под
нагрузкой. Не бизнес, не сервис — чистая библиотека стандартной библиотеки Go
без внешних зависимостей и без инфраструктуры.

## Что внутри

- `internal/limiter/` — ядро: контракт `Limiter` (`Allow() bool` / `AllowN`) и
  реализации алгоритмов. Все безопасны для конкурентного использования.
- `cmd/bench/` — CLI-харнесс: гоняет лимитеры под нагрузкой и печатает
  сравнительную таблицу.

## Статус

MVP собран: Этапы 0–5 завершены. Реализованы и покрыты тестами все четыре
лимитера — `TokenBucket`, `SlidingWindow`, `LeakyBucket` и
`LockFreeTokenBucket` (CAS), — плюс бенчмарк-сьют: микробенчмарки
`internal/limiter/limiter_bench_test.go` и харнесс `cmd/bench`. Гейт
`go build ./... && go vet ./... && go test -race ./...` зелёный, `gofmt -l .`
пусто.

## Быстрый старт (для разработки)

```bash
export PATH="$HOME/sdk/go/bin:$PATH"
go build ./...
go vet ./...
go test -race ./...
go test -bench=. -benchmem ./internal/limiter/   # микробенчмарки
go run ./cmd/bench                               # сравнительная таблица
```

`cmd/bench` без флагов прогоняет все четыре алгоритма подряд (по 2 секунды на
каждый) и печатает таблицу. Флаги: `-algo` (`token`/`sliding`/`leaky`/
`lockfree`/`all`), `-goroutines`, `-rate`, `-capacity`, `-duration`,
`-format` (`text`/`markdown`), `-percentiles`.

Про `-percentiles`: он оборачивает каждый `Allow()` парой `time.Now()`, и эти
накладные расходы сопоставимы со стоимостью самого `Allow()`. Харнесс печатает
об этом предупреждение над таблицей — цифры в режиме перцентилей меряют
«лимитер вместе с измерителем», сравнивать их с цифрами без флага нельзя.
Перцентили считаются по log2-гистограмме фиксированного размера (хранить все
сэмплы нельзя — их десятки миллионов), поэтому p50/p99/p99.9 точны с точностью
до множителя 2.

Окружение: Linux amd64, 11th Gen Intel Core i7-11700 @ 2.50GHz,
`GOMAXPROCS=16`, Go 1.23.4. Числа получены прогоном на машине разработки, а не
на изолированном стенде: абсолютные значения плавают от прогона к прогону,
осмысленны отношения между строками.

### Харнесс — `go run ./cmd/bench -format=markdown`

goroutines=16 rate=1e+09 capacity=1073741824 duration=2s go1.23.4

| algo | goroutines | calls | allowed | denied | throughput (calls/s) | avg latency (ns) | allocs/op (approx) |
|---|---|---|---|---|---|---|---|
| token | 16 | 4035809 | 4035809 | 0 | 2017845 | 7929.3 | 0.00 |
| sliding | 16 | 4270549 | 4270549 | 0 | 2135210 | 7493.4 | 0.00 |
| leaky | 16 | 3951620 | 3951620 | 0 | 1975704 | 8098.4 | 0.00 |
| lockfree | 16 | 1242849 | 1242849 | 0 | 621034 | 25763.5 | 8.26 |

`avg latency (ns)` здесь — это wall-время прогона, умноженное на число горутин
и делённое на число вызовов, то есть среднее время одного вызова с учётом
ожидания; с `ns/op` микробенчмарков оно не совпадает по определению (там это
`elapsed / calls` — обратная агрегированная пропускная способность под
`RunParallel`, без множителя на число горутин).
`allocs/op (approx)` считается по дельте процессных `runtime.MemStats.Mallocs`,
отсюда пометка «approx». `denied = 0` во всех строках — так и задумано: `rate`
и `capacity` заведомо выше нагрузки, чтобы мерить механику допуска, а не
отказы (на пустом бакете lock-free возвращал бы `false` вообще без CAS и без
аллокации, и сравнение оказалось бы подтасовкой в его пользу — если хоть одна
строка всё же денаит, харнесс печатает предупреждение над таблицей).

### Что дал CAS и чего он стоил

**На профиле без отказов (весь этот сьют по построению меряет только путь
допуска) lock-free версия проиграла mutex-версии — примерно втрое по
пропускной способности под 16 горутинами** (621 034 против 2 017 845–2 135 210
вызовов/с; микробенчмарк даёт тот же порядок: 1572 против 454.5–500.0 ns/op).
Отставание заметно и без конкуренции: 344.4 против 216.8–245.7 ns/op на одной
горутине. Путь отказа — ровно то место, где lock-free структурно дешевле
(отказ на пустом бакете возвращает `false` без CAS и без аллокации, см. ниже),
но этот сьют его нигде не измеряет, так что вывод ниже не переносится на
профиль с отказами.

Причина — не только аллокации, колонка `allocs/op` их не разделяет. Первый
вклад виден в ней напрямую: состояние `LockFreeTokenBucket` упаковано в
`atomic.Pointer` на неизменяемый снапшот (решение Этапа 4), и каждая
итерация CAS-петли — успешная или проигранная — выделяет новый снапшот, а
значит каждый ретрай уже произвёл мусор для GC до того, как CAS решил его
судьбу: 1 allocs/op без конкуренции, ~6–8 под нагрузкой. Второй вклад в
колонке не виден: `b.clk.Now()` в `AllowN` (см.
`internal/limiter/lockfree_tokenbucket.go`) стоит внутри цикла ретраев, то
есть чтение часов и пересчёт `nextLockFreeState` повторяются на **каждой**
итерации, а не один раз, как у mutex-версий, которые держат блокировку и
трогают состояние ровно раз. `time.Now()` — заметная доля стоимости `Allow()`
в этом проекте: все три mutex-алгоритма кучно лежат в 216.8–245.7 ns/op на
одной горутине, то есть их общий знаменатель достаточно мал, чтобы стоимость
чтения часов в нём была заметна. При ~6–8 ретраях под нагрузкой lock-free
делает столько же лишних чтений часов и пересчётов состояния, сколько
аллокаций — но по данным этого этапа нельзя сказать, какая доля отставания
приходится на аллокатор/GC, а какая — на повторные чтения часов и
арифметику: замера, который развёл бы эти два вклада, здесь нет. Mutex-версии
не аллоцируют вовсе (0 B/op) и не повторяют чтение часов: держатель блокировки
правит состояние на месте, один раз. В итоге CAS убрал блокировку, но
заменил её и давлением на аллокатор/GC, и повторной работой на каждый ретрай,
и на этом профиле нагрузки размен оказался невыгодным.

Отрицательный результат — это ответ на вопрос проекта, а не провал: цель была
честно измерить цену lock-free подхода, а не получить красивую цифру.
Конфигурация бенчмарка под выгодную картинку не подгонялась. Способы выиграть
у mutex существуют (упаковка состояния в один `uint64` битовыми полями вместо
указателя на снапшот, пулинг снапшотов), но это разговор за пределами MVP: он
требует переоткрыть решение Этапа 4, обоснование которого — в doc-комментариях
`internal/limiter/lockfree_tokenbucket.go` и в
[`docs/plans/stage-4-lockfree-tokenbucket.md`](docs/plans/stage-4-lockfree-tokenbucket.md).

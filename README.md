# ratelimit-lab

Учебная **библиотека rate limiting на Go** с честным бенчмарк-сьютом. Три
классических алгоритма ограничения частоты для одного процесса — **token
bucket**, **sliding window**, **leaky bucket** — плюс два **lock-free**
(CAS-based) варианта token bucket: наивный, с CAS по указателю на снапшот, и
CAS по одному слову с продуманной раскладкой памяти. И сравнение их
throughput/latency под конкурентной нагрузкой.

Это соло pet-проект с приоритетом **обучения**: конкурентные примитивы
(atomic vs mutex vs lock-free CAS-циклы) и алгоритмическая корректность под
нагрузкой. Не бизнес, не сервис — чистая библиотека стандартной библиотеки Go
без внешних зависимостей и без инфраструктуры.

## Что внутри

- `internal/limiter/` — ядро: контракт `Limiter` (`Allow() bool` / `AllowN`) и
  реализации алгоритмов. Все безопасны для конкурентного использования.
- `cmd/bench/` — CLI-харнесс: гоняет лимитеры под нагрузкой и печатает
  сравнительную таблицу.

## Статус

MVP собран: Этапы 0–6 завершены. Реализованы и покрыты тестами пять
лимитеров — `TokenBucket`, `SlidingWindow`, `LeakyBucket`,
`LockFreeTokenBucket` (CAS по указателю на снапшот) и `AtomicTokenBucket`
(CAS по одному слову), — плюс бенчмарк-сьют: микробенчмарки
`internal/limiter/limiter_bench_test.go` и харнесс `cmd/bench`. Гейт
`go build ./... && go vet ./... && go test -race ./...` зелёный, `gofmt -l .`
пусто.

## Быстрый старт (для разработки)

```bash
export PATH="$HOME/sdk/go/bin:$PATH"
go build ./...
go vet ./...
go test -race ./...
go test -bench=. -benchmem ./internal/limiter/   # микробенчмарки
go run ./cmd/bench                               # сравнительная таблица
```

`cmd/bench` без флагов прогоняет все пять алгоритмов подряд (по 2 секунды на
каждый, в фиксированном порядке — чтобы таблицы были diff-абельны) и печатает
таблицу.

| Флаг | Дефолт | Что задаёт |
|---|---|---|
| `-algo` | `all` | `token` / `sliding` / `leaky` / `lockfree` / `atomic` / `all` |
| `-goroutines` | `runtime.GOMAXPROCS(0)` | число горутин, создающих нагрузку |
| `-rate` | `1e9` | скорость refill/слива в секунду |
| `-capacity` | `1<<30` | ёмкость бакета (**для `sliding` не применяется**) |
| `-duration` | `2s` | длительность нагрузки на алгоритм |
| `-format` | `text` | `text` (выровненная таблица) или `markdown` (GFM) |
| `-percentiles` | выкл. | добавить p50/p99/p99.9 |

Про `sliding`: `NewSlidingWindow` принимает `(limit, window)`, а не
`(rate, capacity)`, поэтому харнесс трактует `-rate` как лимит на жёстко
зашитое окно в 1 секунду, а `-capacity` для него игнорирует. Отсюда
дополнительное требование `1 <= -rate <= math.MaxInt64`, когда `sliding` в
списке: дробная скорость усеклась бы до нулевого лимита и денаила всё.
Сигнатуры конструкторов ради удобства харнесса не выравниваются — они отражают
разную природу алгоритмов (подробности — [`docs/POST_MVP_PLAN.md`](docs/POST_MVP_PLAN.md) §4а).

Про `atomic`: `NewAtomicTokenBucket` хранит период эмиссии целыми
наносекундами (`round(1e9/rate)`) и произведение `capacity × период` — тоже, и
паникует на параметрах, которые в это не укладываются. Поэтому, когда `atomic`
в списке, харнесс требует `-rate <= 2e9` (иначе период меньше наносекунды) и
`round(1e9/-rate) × -capacity <= 2^62` (иначе размах бакета переполняет int64 —
классическая ловушка вида «одна операция в час с бёрстом в миллионы»). Обе
границы продублированы в `parseConfig`, чтобы опечатка в CLI давала диагностику
и код возврата 1, а не стек паники.

Про `-percentiles`: он оборачивает каждый `Allow()` парой `time.Now()`, и эти
накладные расходы сопоставимы со стоимостью самого `Allow()`. Харнесс печатает
об этом предупреждение над таблицей — цифры в режиме перцентилей меряют
«лимитер вместе с измерителем», сравнивать их с цифрами без флага нельзя.
Перцентили считаются по log2-гистограмме фиксированного размера (хранить все
сэмплы нельзя — их десятки миллионов), поэтому p50/p99/p99.9 точны с точностью
до множителя 2.

## Результаты бенчмарков

Окружение: Linux amd64, 11th Gen Intel Core i7-11700 @ 2.50GHz,
`GOMAXPROCS=16`, Go 1.23.4. Числа получены прогоном на машине разработки, а не
на изолированном стенде: абсолютные значения плавают от прогона к прогону,
осмысленны отношения между строками.

Числа сняты одним прогоном одной сборки на этой машине разработки (не на
изолированном стенде): значения lock-free реализаций между сборками
несравнимы — один и тот же исходник давал разброс 591…976 нс в шести разных
бинарях в рамках этого же проекта. Разрешающая способность стенда — порядка
10%, поэтому осмысленны кратные отношения между строками одного прогона, а не
малые различия. Строки `Baseline_*` не декоративные: без них serial-числа
интерпретируются неверно, потому что одно чтение часов (`Baseline_ClockNow` /
`Baseline_ClockSince`) само по себе сопоставимо по стоимости со всей операцией
допуска.

| algo | goroutines | calls | allowed | denied | throughput (calls/s) | avg latency (ns) | allocs/op (approx) |
|---|---|---|---|---|---|---|---|
| token | 16 | 4502520 | 4502520 | 0 | 2251089 | 7107.7 | 0.00 |
| sliding | 16 | 4643002 | 4643002 | 0 | 2321443 | 6892.3 | 0.00 |
| leaky | 16 | 4410605 | 4410605 | 0 | 2205095 | 7255.9 | 0.00 |
| lockfree | 16 | 1326101 | 1326101 | 0 | 661894 | 24173.0 | 9.29 |
| atomic | 16 | 10385593 | 10385593 | 0 | 5150932 | 3106.2 | 0.00 |

`avg latency (ns)` здесь — это wall-время прогона, умноженное на число горутин
и делённое на число вызовов, то есть среднее время одного вызова с учётом
ожидания; с `ns/op` микробенчмарков оно не совпадает по определению (там это
`elapsed / calls` — обратная агрегированная пропускная способность под
`RunParallel`, без множителя на число горутин).
`allocs/op (approx)` считается по дельте процессных `runtime.MemStats.Mallocs`,
отсюда пометка «approx». `denied = 0` во всех строках — так и задумано: `rate`
и `capacity` заведомо выше нагрузки, чтобы мерить механику допуска, а не
отказы (на пустом бакете lock-free возвращал бы `false` вообще без CAS и без
аллокации, и сравнение оказалось бы подтасовкой в его пользу — если хоть одна
строка всё же денаит, харнесс печатает предупреждение над таблицей).

### Что дал CAS и чего он стоил

Три точки сравнения на одном и том же профиле нагрузки (без отказов — весь
этот сьют по построению меряет только путь допуска): mutex-версии (Этапы
1–3), наивный CAS по указателю на снапшот (`LockFreeTokenBucket`, Этап 4) и
CAS по одному слову с продуманной раскладкой памяти (`AtomicTokenBucket`,
Этап 6).

**Наивный CAS проиграл mutex-версиям — примерно втрое по пропускной
способности под 16 горутинами** (661 894 против 2 205 095–2 321 443
вызовов/с; микробенчмарк даёт тот же порядок: 1435 против 470.3–487.1 ns/op).
Отставание заметно и без конкуренции: 346.7 против 212.4–239.1 ns/op на одной
горутине. Это задокументированный результат Этапа 4/5, а не недоделка:
реализация остаётся контрольной точкой «наивный CAS» и не оптимизируется.

Причина — не только аллокации, колонка `allocs/op` их не разделяет. Первый
вклад виден в ней напрямую: состояние `LockFreeTokenBucket` упаковано в
`atomic.Pointer` на неизменяемый снапшот, и каждая итерация CAS-петли —
успешная или проигранная — выделяет новый снапшот, а значит каждый ретрай уже
произвёл мусор для GC до того, как CAS решил его судьбу: ~1 allocs/op без
конкуренции, ~9 под нагрузкой. Второй вклад в колонке не виден: `b.clk.Now()`
в `AllowN` (см. `internal/limiter/lockfree_tokenbucket.go`) стоит внутри цикла
ретраев, то есть чтение часов и пересчёт `nextLockFreeState` повторяются на
**каждой** итерации, а не один раз, как у mutex-версий, которые держат
блокировку и трогают состояние ровно раз.

**`AtomicTokenBucket` (Этап 6) обгоняет mutex-версии на этом же профиле**:
5 150 932 вызовов/с под 16 горутинами против 2 205 095–2 321 443 у
mutex-версий и 661 894 у наивного CAS; на одной горутине — 118.6 нс/оп против
212.4–239.1 у mutex и 346.7 у наивного CAS, при `0 allocs/op` в обоих
профилях. Главный вывод: **отставание Этапа 5 было следствием раскладки
памяти и представления состояния, а не природы lock-free подхода как
таковой.** Ту же идею (CAS вместо мьютекса) можно реализовать так, что она
обгонит mutex, если убрать источники накладных расходов, которые несёт именно
конкретная реализация Этапа 4, а не CAS вообще.

Четыре приёма, каждый измеренно необходим (детали и цифры конкретных сборок —
в doc-комментариях `internal/limiter/atomic_tokenbucket.go` и
[`docs/plans/stage-6-fast-lockfree.md`](docs/plans/stage-6-fast-lockfree.md)):

1. **Состояние в одном слове** (`atomic.Int64`, время вместо токенов) — ноль
   аллокаций на любом пути, в отличие от снапшота Этапа 4.
2. **Часы читаются один раз до петли**, а не на каждом ретрае: проигранный
   CAS переиспользует уже снятое время вместо нового чтения.
3. **Константные поля вынесены в локальные переменные до петли**: после
   проигранного CAS (полный барьер памяти) компилятор иначе обязан
   перечитывать их из кэш-линии, которую как раз инвалидируют конкурентные
   писатели.
4. **Падинг 128 байт** между целью CAS и read-only полями — гарантирует хотя
   бы одну целую нетронутую кэш-линию между ними при любом выравнивании кучи
   (64 байта измеренно хуже отсутствия падинга вовсе: парный префетч соседних
   линий всё равно достаёт до `line+1`).

Отрицательный результат Этапа 5 и положительный Этапа 6 — оба ответы на
вопрос проекта, а не провал или удача: цель была честно измерить цену разных
lock-free представлений, а не получить красивую цифру. Конфигурация
бенчмарка под выгодную картинку не подгонялась.

## Конструкторы — сигнатуры не единообразны

Три лимитера из четырёх принимают `(rate float64, capacity int, clk Clock)`:

- `NewTokenBucket(rate float64, capacity int, clk Clock)`
- `NewLeakyBucket(rate float64, capacity int, clk Clock)`
- `NewLockFreeTokenBucket(rate float64, capacity int, clk Clock)`

А четвёртый — **другой**:

- `NewSlidingWindow(limit int, window time.Duration, clk Clock)`

Это важно для флага `-algo` в `cmd/bench`: единый драйвер не сведётся к одной
сигнатуре, нужен слой отображения «параметры CLI → конструктор». Пересматривать
сигнатуры ради единообразия не надо — они отражают разную природу алгоритмов.

## Три ловушки, которые обесценят сравнение

**1. `fakeClock` в бенчмарках использовать нельзя.** Он берёт мьютекс на каждом
`Now()` (`internal/limiter/clock_test.go:19`) — под `b.RunParallel` это
сериализует все горутины на нём самом, и сравнение mutex против lock-free
измерит `fakeClock`, а не лимитеры. Брать `SystemClock`, как в примере SKILL §6.
Детерминизм в бенчмарках не нужен: это замер, а не проверка корректности.

**2. Ёмкость должна быть велика — и для lock-free это асимметрично важнее.**
SKILL §6 требует большой ёмкости, чтобы мерить механику, а не отказы. После
Этапа 4 у этого правила появилось второе дно: в `LockFreeTokenBucket` отказ
возвращает `false` **без CAS и без аллокации**, тогда как mutex-версия и на
отказе берёт мьютекс. Бенчмарк на опустевшем бакете померил бы у lock-free
дешёвый путь `Load + Now + арифметика`, а у baseline — полный захват блокировки,
и дал бы lock-free незаслуженное преимущество в разы. Держать бакет непустым
(`rate` и `capacity` заведомо больше нагрузки), иначе цифры — артефакт.

**3. Мерить аллокации, а не только время.** Выбранная в Этапе 4 упаковка
состояния (`atomic.Pointer` на неизменяемый снапшот) стоит **одной аллокации на
итерацию CAS-петли**, а под contention ретраи её умножают. Это осознанно
принятая цена, и Этап 5 — то место, где она должна стать видимой: `b.ReportAllocs()`
обязателен, `allocs/op` идёт в таблицу наравне с `ns/op`.

## Ожидаемый результат — и почему отрицательный тоже годится

Вероятный исход: под высокой конкуренцией lock-free проиграет mutex-версии на
аллокациях и давлении на GC. **Это не провал этапа.** Заявленная цель проекта —
честное сравнение «что дал CAS и чего он стоил» (`TECHNICAL_PLAN.md` §5,
`PLAN.md`), а отрицательный результат отвечает на этот вопрос ровно так же
хорошо, как положительный. В README идут фактические числа с объяснением
причины, а не подгонка конфигурации до выгодной картинки. SKILL §6 прямо
запрещает микрооптимизировать под бенчмарк ценой корректности.

Если захочется «исправить» проигрыш — это уже post-MVP разговор про пулинг
снапшотов или упаковку в `uint64`, и он требует переоткрыть решение Этапа 4,
а не подкрутить бенчмарк.

### Решения, принятые в этом плане

- **Микробенчмарки — один файл** `internal/limiter/limiter_bench_test.go`
  (имя удовлетворяет конвенции SKILL §6 `*_bench_test.go`). Не по файлу на
  алгоритм: честность сравнения держится на том, что все четыре лимитера
  проходят через **общие** хелперы `benchSerial`/`benchParallel` — один цикл,
  один профиль нагрузки. Четыре файла продублировали бы цикл и разъехались бы
  при первой же правке. Правило «по файлу на алгоритм» (SKILL §1) — про
  реализации, не про бенчмарки.
- **`-algo` по умолчанию — `all`: прогон всех четырёх подряд.** Смысл бинарника —
  сравнительная таблица для README; запуск без флагов должен давать именно её,
  а не один столбец без точки сравнения. Одиночный алгоритм — явным флагом.
- **Оркестрация живёт в `package main`, но в трёх файлах** внутри `cmd/bench/`:
  `main.go` (флаги, отображение algo→конструктор, wiring), `runner.go` (драйвер
  нагрузки и сбор метрик), `report.go` (гистограмма перцентилей + рендереры
  text/markdown). Новых пакетов не заводить: логика бенч-специфична, из других
  мест не нужна, а `go test ./cmd/bench` прекрасно тестирует и `package main`.
  Это не нарушает TECHNICAL_PLAN §2: алгоритмической логики лимитеров здесь нет,
  только оркестрация — просто разложенная по файлам для читаемости и тестов.
- **`allocs/op` показывается и в `cmd/bench`**, не только в микробенчмарках:
  дельта `runtime.MemStats.Mallocs` до/после прогона, делённая на число вызовов.
  Смысл этапа — сделать цену снапшот-аллокации lock-free видимой; таблица без
  этой колонки прячет главный результат. Значение приближённое (процессное),
  в выводе колонка так и подписывается: `allocs/op (approx)`.

### 1. Микробенчмарки — `internal/limiter/limiter_bench_test.go`

Новый файл в `package limiter`. Существующие файлы пакета не трогать.

Общие хелперы (лимитер конструируется в вызывающей функции; вызов через
интерфейс `Limiter` — одинаковый косвенный вызов для всех четырёх, честно):

```go
func benchSerial(b *testing.B, lim Limiter) {
    b.ReportAllocs()
    b.ResetTimer()
    for i := 0; i < b.N; i++ { lim.Allow() }
}

func benchParallel(b *testing.B, lim Limiter) {
    b.ReportAllocs()
    b.ResetTimer()
    b.RunParallel(func(pb *testing.PB) {
        for pb.Next() { lim.Allow() }
    })
}
```

Восемь top-level функций (grep-ается, фильтруется `-bench=Parallel`):
`BenchmarkTokenBucket_Serial`, `BenchmarkTokenBucket_Parallel`,
`BenchmarkSlidingWindow_Serial`, `BenchmarkSlidingWindow_Parallel`,
`BenchmarkLeakyBucket_Serial`, `BenchmarkLeakyBucket_Parallel`,
`BenchmarkLockFreeTokenBucket_Serial`, `BenchmarkLockFreeTokenBucket_Parallel`.

Конструирование — с `SystemClock` (не `fakeClock` — ловушка 1 брифа) и
заведомо непустым бакетом (ловушка 2):

- token / leaky / lockfree: `New*(1e9, 1<<30, SystemClock)` — refill быстрее
  любого потребления, отказов нет, меряем механику admission-пути.
- sliding: `NewSlidingWindow(1<<40, time.Hour, SystemClock)` — лимит заведомо
  больше максимального `b.N` (~1e9), окно за прогон не переворачивается;
  меряется горячий путь допуска, а не rollover. `1<<40` точно представимо в
  float64, взвешенная оценка не страдает.

Бенчмаркается только `Allow()`; `AllowN` отдельно не меряем (тот же код-путь,
`Allow` — это `AllowN(1)`).

### 2. `cmd/bench` — заменить содержимое `main.go`, добавить `runner.go`, `report.go`

#### 2.1 Флаги и конфиг (`main.go`)

Парсинг — через `flag.NewFlagSet(...)`, а не глобальный `flag.CommandLine`,
чтобы тестировать без глобального состояния:

```go
type config struct {
    algos       []string      // развёрнутый список: одно имя либо все четыре
    goroutines  int
    rate        float64
    capacity    int
    duration    time.Duration
    format      string        // "text" | "markdown"
    percentiles bool
}

func parseConfig(args []string) (config, error)
```

| Флаг | Тип | Дефолт | Смысл |
|---|---|---|---|
| `-algo` | string | `all` | `token`, `sliding`, `leaky`, `lockfree` или `all` |
| `-goroutines` | int | `runtime.GOMAXPROCS(0)` | число горутин нагрузки |
| `-rate` | float64 | `1e9` | rate конструкторов; заведомо выше нагрузки (ловушка 2) |
| `-capacity` | int | `1 << 30` | capacity конструкторов |
| `-duration` | duration | `2s` | длительность прогона **одного** алгоритма |
| `-format` | string | `text` | `text` (tabwriter) или `markdown` |
| `-percentiles` | bool | `false` | включить p50/p99/p99.9 (per-call timing) |

Дефолтный запуск: 4 алгоритма × 2s ≈ 8–9 секунд суммарно — осмысленная таблица
за «единицы секунд». Валидация с ошибкой (не паникой): неизвестный `-algo` или
`-format`, `goroutines < 1`, `rate <= 0`, `capacity < 1`, `duration <= 0`.

#### 2.2 Отображение algo → конструктор (`main.go`)

```go
func makeLimiter(algo string, cfg config) (limiter.Limiter, error)
```

- `token`    → `limiter.NewTokenBucket(cfg.rate, cfg.capacity, limiter.SystemClock)`
- `leaky`    → `limiter.NewLeakyBucket(cfg.rate, cfg.capacity, limiter.SystemClock)`
- `lockfree` → `limiter.NewLockFreeTokenBucket(cfg.rate, cfg.capacity, limiter.SystemClock)`
- `sliding`  → `limiter.NewSlidingWindow(int(cfg.rate), time.Second, limiter.SystemClock)`
  — сигнатура другая (см. бриф): окно фиксируем в 1s, лимит берём из `-rate`,
  тогда устойчивая пропускная способность (`limit/window`) совпадает по смыслу
  с `rate` остальных. `-capacity` для sliding не используется — отметить это в
  usage-тексте флага `-algo`, сигнатуру `NewSlidingWindow` **не менять**.

Порядок прогона при `all` фиксированный: `token, sliding, leaky, lockfree`.

#### 2.3 Драйвер нагрузки и метрики (`runner.go`)

```go
type result struct {
    algo           string
    calls, allowed uint64
    elapsed        time.Duration
    allocs         uint64       // дельта MemStats.Mallocs за прогон
    hist           *latencyHist // nil, если -percentiles выключен
}

func runOne(algo string, lim limiter.Limiter, cfg config) result
```

Устройство:

- **Остановка по времени** — `atomic.Bool` stop-флаг, взводится
  `time.AfterFunc(cfg.duration, ...)`; горутины проверяют `stop.Load()` на
  каждой итерации. Load почти-только-читаемой переменной дёшев и contention не
  создаёт; per-call `time.Now()` для дедлайна не нужен.
- **Счётчики без contention (требование постановки):** никаких общих
  `atomic.Add` в горячем цикле. Каждая горутина копит `calls`/`allowed` (и свою
  `latencyHist`) в **локальных переменных** и один раз, после выхода из цикла,
  записывает их в свой элемент заранее выделенного `[]workerResult` (индекс —
  номер горутины; писатели не пересекаются, false sharing в горячем цикле
  отсутствует, потому что записи нет до самого конца). Агрегация — после
  `wg.Wait()`. Замечание для ревью: запрет SKILL §5 на локальное накопление
  относится к **stress-тестам**, где contention — предмет проверки; здесь
  contention на лимитере и есть измеряемое, а счётчики обязаны быть вне замера.
- **Два варианта тела цикла**, выбор до цикла (ветка не в горячем пути):
  без перцентилей — `lim.Allow()` и инкременты; с перцентилями —
  `t := time.Now(); ok := lim.Allow(); h.observe(time.Since(t))`.
- **Аллокации:** `runtime.GC()`, `runtime.ReadMemStats(&m0)` до старта горутин;
  `runtime.ReadMemStats(&m1)` после `wg.Wait()`; `allocs = m1.Mallocs - m0.Mallocs`.
- `elapsed = time.Since(start)` фактический (не `cfg.duration`); throughput и
  среднее считаются от него.

Производные метрики (считает рендерер, не драйвер):
`denied = calls - allowed`; `throughput = calls / elapsed.Seconds()`;
`avg ns/op = float64(elapsed.Nanoseconds()) * goroutines / calls` (wall-время ×
работники / вызовы — приближение среднего времени одного вызова);
`allocs/op = allocs / calls`.

#### 2.4 Гистограмма перцентилей (`report.go`)

Хранение всех сэмплов запрещено постановкой — log2-гистограмма фиксированного
размера, ноль аллокаций в горячем цикле:

```go
type latencyHist struct{ buckets [64]uint64 }

func (h *latencyHist) observe(d time.Duration) // индекс = bits.Len64(uint64(d.Nanoseconds())), кламп в [0,63]
func (h *latencyHist) merge(o *latencyHist)    // поэлементная сумма
func (h *latencyHist) quantile(q float64) time.Duration // верхняя граница бакета, накрывающего q-квантиль
```

Разрешение — степени двойки (ответ точен до ×2); для сравнения алгоритмов между
собой этого достаточно, и это честнее, чем изображать наносекундную точность.
p50/p99/p99.9 — `quantile(0.50/0.99/0.999)`.

**Обязательная строка-предупреждение** (в обоих форматах, над таблицей), когда
`-percentiles` включён, примерно такая:

```
note: -percentiles adds a time.Now() pair around every Allow() call; this
overhead is comparable to the cost of Allow() itself and is included in ALL
reported figures (throughput, avg, percentiles).
```

Цифры с перцентилями честно объявляются «замером вместе с измерителем», а не
выдаются за бесплатные.

#### 2.5 Рендереры (`report.go`)

```go
func renderText(w io.Writer, rs []result, cfg config) error     // text/tabwriter, выровненные колонки
func renderMarkdown(w io.Writer, rs []result, cfg config) error // готовая GFM-таблица для README
```

Колонки (одинаковый набор в обоих форматах):
`algo | goroutines | calls | allowed | denied | throughput (calls/s) | avg ns/op | allocs/op (approx)`,
плюс `p50 | p99 | p99.9` только при `-percentiles`. Перед таблицей — одна
строка контекста прогона: `goroutines=8 rate=1e9 capacity=1073741824 duration=2s go1.23`.
Вывод — в `os.Stdout`; `main()` сводится к `parseConfig` → цикл
`makeLimiter`/`runOne` → рендерер, ошибки — в `os.Stderr` c exit code 1.

### 3. Тесты `cmd/bench` (`cmd/bench/main_test.go`, `report_test.go`)

Покрываем чистую логику, не превращая CLI во фреймворк. Драйвер по-настоящему
проверяется глазами на реальном запуске (см. критерий готовности), тестом — лишь smoke.

- `parseConfig`: дефолты (algo=all разворачивается в 4, format=text,
  percentiles=false); каждая ветка валидации даёт ошибку (`-algo=bogus`,
  `-format=bogus`, `-goroutines=0`, `-rate=0`, `-duration=0`); одиночный
  `-algo=lockfree` даёт список из одного.
- `makeLimiter`: для каждого из 4 имён — не-nil лимитер нужного конкретного
  типа (type assertion); sliding получает `limit == int(cfg.rate)` и окно 1s
  (проверить через поведение необязательно — достаточно, что конструктор
  вызван без паники и вернул `*limiter.SlidingWindow`); неизвестное имя — ошибка.
- `latencyHist`: `observe`+`quantile` на синтетике (все значения в одном
  бакете → квантиль равен его верхней границе; два бакета 90/10 → p50 в первом,
  p99 во втором); `merge` суммирует; пустая гистограмма не паникует.
- Рендереры: писать в `bytes.Buffer`; markdown-вывод содержит строку-заголовок,
  разделитель `|---|` и по строке на алгоритм; text-вывод содержит имена
  алгоритмов и заголовки колонок; колонки перцентилей появляются только при
  `cfg.percentiles`; предупреждение об overhead присутствует тогда и только
  тогда, когда `cfg.percentiles == true`.
- Smoke на драйвер: `runOne` с `goroutines=2`, `duration=20ms`, token bucket на
  `SystemClock` → `calls > 0`, `allowed > 0`, `allowed <= calls`, elapsed в
  разумных пределах. Никаких ассертов на конкретные числа — тест не должен
  флейкать.

- Сигнатуры конструкторов (включая «неудобный» `NewSlidingWindow`) и любые
  реализации в `internal/limiter/*.go`.
- Решения Этапа 4: `atomic.Pointer`-снапшот и «отказ без CAS» — их цена как раз
  и должна стать видимой, а не спрятанной.
- `fakeClock` и существующие тесты; `clock_test.go` не менять.
- Никаких внешних зависимостей, никакого `pkg/`.

### 6. Критерий готовности

1. `go test -bench=. -benchmem ./internal/limiter/` печатает 8 строк с
   `ns/op` и `allocs/op` (ReportAllocs действует).
2. `go run ./cmd/bench` без флагов печатает сравнительную таблицу по 4
   алгоритмам за единицы секунд; `-format=markdown` даёт валидную GFM-таблицу;
   `-percentiles` добавляет p50/p99/p99.9 и строку-предупреждение об overhead.
   Проверяется реальным запуском и глазами, не только компиляцией.
3. README дополнен реальными числами и интерпретацией.
4. Общий гейт: `go build ./... && go vet ./... && go test -race ./...` чисто,
   `gofmt -l .` пусто. Существующие тесты пакета `limiter` не изменены и зелёные.

## Итог

Этап закрыт 2026-08-22. План исполнен без содержательных отклонений: один файл
микробенчмарков, `-algo=all` по умолчанию, оркестрация в `package main` тремя
файлами, log2-гистограмма перцентилей. Мелкие добавления сверх плана: `-h`
печатает usage и выходит с кодом 0; `result` носит `workers`, чтобы рендерер
считал среднюю латентность без второй ссылки на конфиг.

Решения, принятые автором до планирования: `-format=text|markdown` (text по
умолчанию) и latency = среднее всегда + перцентили только по флагу
`-percentiles`. Второе — потому что per-call `time.Now()` стоит примерно
столько же, сколько сам `Allow()`, и включать его в дефолтный замер значит
мерить измеритель.

### Что изменило независимое ревью

Ревью дало 23 находки (0 блокеров). Принято 7, каждая проверена по `file:line`
перед правкой:

- **Warning при `denied > 0`** в обоих рендерерах. Ловушка 2 брифа до этого
  была защищена только словами в доке: `-capacity=1` проходил валидацию, и
  пользователь получил бы таблицу, где lock-free «выигрывает», без единого
  слова о том, почему она недействительна.
- **Атрибуция причины в README была неполной.** Текст объяснял проигрыш
  lock-free одними аллокациями, но `b.clk.Now()` стоит **внутри** CAS-петли
  (`lockfree_tokenbucket.go:125`) и выполняется на каждом ретрае — при ~7
  ретраях это семь чтений часов там, где mutex-версии делают одно. Колонка
  `allocs/op` два вклада не разделяет, и README теперь говорит это прямо,
  вместо того чтобы выдавать одну из гипотез за установленную причину.
- **Колонка `avg ns/op` переименована в `avg latency (ns)`**: формула
  `elapsed * workers / calls` даёт среднюю латентность вызова, а `ns/op` из
  `go test -bench` под `RunParallel` — это `elapsed / calls`, обратная
  агрегированная пропускная способность. Разница ровно в `workers` (16× в
  наших числах), и старое имя приглашало сравнить несравнимое.
- Оговорка «на профиле без отказов» в жирный тезис README; валидация `-rate`
  для sliding (`-rate=0.5` давал `NewSlidingWindow(0, ...)`, молча отказывающий
  всему); фраза в `percentileNote` о том, что режим перцентилей систематически
  сближает строки; удалено мёртвое поле `result.dur`.

Отклонено осознанно: замечание о «подозрительно медленных» абсолютных числах
(рассуждение о нормах, не измерение; провенанс-шапку `goos/goarch/cpu` в README
вернули, а перепрогон на изолированном стенде — не наша среда), разгон воркеров
внутри измеряемого окна (симметричен для всех четырёх и пренебрежим на 2с),
процессный учёт аллокаций (сам ревьюер пишет «фикс не нужен»), недостижимые
защитные ветки и стилистика. `1 << 40` не соберётся на 32-битной платформе —
у проекта нет такой цели.

### Что осталось неизмеренным (осознанно)

Сьют по построению меряет **только путь допуска**. Путь отказа — ровно то
место, где lock-free структурно дешевле, — не меряет ни микробенчмарк, ни
харнесс. Насколько дешевле, видно из прогона с `-rate=1000 -capacity=1`:
lock-free даёт ~55M вызовов/с против ~2M у mutex-версий, то есть 27×, целиком
за счёт `false` без CAS и без аллокации. Отдельные `Benchmark*_Denied` в MVP не
заводились: цель Этапа — цена CAS на рабочем пути, а не полный профиль. Если
понадобится честный размен в обе стороны — это первый кандидат в post-MVP.

Разделить вклад аллокации снапшота от вклада повторного чтения часов на
ретраях этими данными нельзя. Для этого нужен счётчик итераций CAS-петли в
бенчмарк-обвязке (не в лимитере) — тоже post-MVP, и он же предпосылка к любому
разговору про упаковку состояния в `uint64` или пулинг снапшотов.

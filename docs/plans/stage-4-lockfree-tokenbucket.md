## Два подводных камня, оплаченных предыдущими этапами

Оба стоили реальной отладки на Этапах 2–3 — не переоткрывать.

**1. Сравнение допуска писать сразу с `admitEpsilon`.** Все лимитеры хранят
состояние накопительным `float64`. Строгое сравнение даёт измеримый недобор:
клиент на настроенной скорости с не-двоично-точным шагом (`rate` 1/с, опрос
каждые 100 мс) после слива целой единицы оставляет остаток ~1.4e-16, каждый
граничный запрос денаится — **910 допусков вместо 1000, ~9% недобора**,
замерено и в token bucket, и в leaky bucket. Константа `admitEpsilon = 1e-9`
живёт в `internal/limiter/limiter.go` и общая для всех реализаций. Её граница
применимости: при лимите от 2^24 шаг `float64` равен 3.7e-9, `capacity+1e-9 ==
capacity`, и эпсилон молча становится no-op — осознанно не чинится
относительным эпсилоном, лимиты проекта считают запросы, а не байты.

**2. Тест на дрейф — с не-двоично-точным шагом.** Табличные тесты с двоично
точными `rate`/шагом этот дефект **не ловят**: он проходит мимо них целиком.
Нужен отдельный кейс по образцу `TestLeakyBucket_SteadyStateNonBinaryExactStep`
в `internal/limiter/leakybucket_test.go`.

## Счётчики в стресс-тестах

`SKILL.md` §5 (после #7) запрещает не только `int` под mutex, но и обходной
вариант «копить в локальной переменной, слить один раз после цикла». Причина
не стилистическая: в стресс-тесте лимитера contention и есть предмет измерения,
локальное накопление снимает с горутин ровно то давление на общее состояние,
ради которого тест написан, и тем сильнее, чем больше `callsPer`. Считать
`allowed.Add(1)` на каждый допуск.

Мотив записать это отдельно: паттерн уже копировался из теста в тест — так были
написаны все три `*_ConcurrentNoOverAdmit` до #5. В Этапе 4 стресс-тесты новые,
соблазн вернётся.

## Открытые решения (за автором, не за планировщиком)

- **Упаковка состояния:** `atomic.Pointer[state]` на неизменяемый снапшот
  **или** битовые поля в одном `uint64`. Плюсы/минусы зафиксировать при
  реализации в комментарии/коммите.
- **Backoff при неудачном CAS** — SKILL §5 намеренно не предписывает стратегию.

## Критерий готовности

Из `TECHNICAL_PLAN.md`: стресс-тест стабильно зелёный под `-race` с `-count>1`
и `GOMAXPROCS>1`, инвариант «суммарно разрешённых ≤ `capacity`» не нарушается.
Плюс общий гейт проекта: `go build ./... && go vet ./... && go test -race ./...`

объёме, что у `TokenBucket`: включая пометку о непригодности нулевого значения
(нет Clock → nil dereference; construct with NewLockFreeTokenBucket) и фразу
про безопасность конкурентного использования.

### Семантическое равенство с `TokenBucket` — главное ограничение

Наблюдаемое поведение обязано совпадать с mutex-baseline
(`internal/limiter/tokenbucket.go`), проверяется теми же свойствами тестов:

- **Refill-математика:** `elapsed := now.Sub(last)`;
  `tokens = min(capacity, tokens + elapsed.Seconds()*rate)`; кламп по
  `capacity` сверху. Бакет стартует полным, метка времени — `clk.Now()` в
  конструкторе. Фоновых горутин нет — refill только арифметикой при вызове.
- **Сравнение допуска — сразу с `admitEpsilon`**
  (`tokens+admitEpsilon >= float64(n)`), не «потом добавим». Константа общая,
  живёт в `limiter.go`; её обоснование и граница (лимиты ≥ 2^24) — там же в
  doc-комментарии, пере-документировать не нужно, достаточно сослаться, как это
  делает `TokenBucket.AllowN`.
- **`AllowN(n <= 0) -> true` вообще без касания состояния** — включая метку
  времени. Ранний return до чтения состояния. У baseline это пришпилено тестом
  `TestTokenBucket_AllowNNonPositiveKeepsRefillTimestamp` — здесь нужен аналог.
- **Батч all-or-nothing:** отказ не списывает ничего.
- **`Allow()` = `return b.AllowN(1)`** — вся логика в `AllowN` (SKILL §2).
- **Обратный ход часов не детектируется** — то же осознанное допущение, что у
  соседей: контракт `Clock` (см. doc-комментарий в `limiter.go`) требует
  неубывающего `Now`, реализации на это полагаются.

**Одно допустимое расхождение с baseline, зафиксировать в комментарии:**
канонический цикл SKILL §5 при отказе возвращает `false` **без** CAS —
состояние (включая метку времени) при денае не обновляется, тогда как
mutex-версия персистит refill и на отказе. Это эквивалентно наблюдаемо **с
точностью до порога `admitEpsilon`**: следующий вызов пересчитает refill от
более старой метки за больший `elapsed`, и накопленный кредит — то же
вещественное число (`min(cap, x+a+b) == min(cap, min(cap, x+a)+b)` при
`a, b >= 0`). Разойтись вердикты могут только у конфигурации, севшей ровно на
порог эпсилона, — зато систематически: при `capacity=1`, `rate=0.5`, `AllowN(1)`
каждые `333333333` нс lock-free допускает на ~7% меньше, чем baseline (найдено
ревью Этапа 4 перебором и проверено численно). Не «чинить» это принудительным CAS на денае —
иначе отказ начнёт крутиться в петле и проигрывать конкурентам, которые ему
ничего не должны. Ревью может принять расхождение за баг — поэтому комментарий
в коде обязателен.

### Структура CAS-цикла — рамки

- Канонический цикл — SKILL §5: `load → computeNext(old, now) → CAS → retry`;
  `now` берётся один раз до петли или на каждой итерации — выбор исполнителя,
  но помнить: `fakeClock.Now()` берёт мьютекс, в stress-тесте это источник
  contention сам по себе.
- **`computeNext` — чистая функция без side-effect:** старое состояние + `now`
  на входе, новое состояние + вердикт на выходе. Весь недетерминизм — только в
  петле. Это условие осмысленности stress-теста, не стилистика.
- Никаких read-modify-write без CAS, никаких «значение не менялось, можно не
  проверять» (ABA/потерянные обновления — TECHNICAL_PLAN §5).

### Открытые решения — за исполнителем

Оба помечены открытыми ещё в брифе; выбор сделать при реализации и
зафиксировать плюсы/минусы в комментарии или сообщении для коммита.

**1. Упаковка состояния** (токены + метка времени, обновляемые одним CAS):

- `atomic.Pointer[state]` на неизменяемый снапшот. Плюсы: токены остаются
  `float64` без потери точности — арифметика бит-в-бит совпадает с baseline, и
  семантическое равенство (включая дрейф-тест) получается даром; `time.Time`
  хранится целиком; ABA невозможна структурно — пока старый указатель жив в
  петле, GC не отдаст его адрес новому объекту. Минусы: аллокация снапшота на
  каждую итерацию петли → давление на GC, которое проявится в бенчмарках
  Этапа 5 именно под contention — там, где lock-free должен показывать себя.
- Битовые поля в одном `uint64`. Плюсы: ноль аллокаций, один word, дёшево под
  contention. Минусы: `float64` токенов сам занимает все 64 бита — придётся
  квантовать и токены (fixed-point), и метку времени (наносекунды от старта,
  усечённые биты), а это **другая арифметика**, чем у baseline: семантическое
  равенство и `admitEpsilon`-граница перестают получаться автоматически, их
  придётся доказывать заново, и дрейф-тест с не-двоично-точным шагом обязан
  пройти на квантованной схеме. Отдельно теряется монотонная составляющая
  `time.Time` при конвертации в наносекунды.

Какой бы вариант ни был выбран, ограничение одно: **свойства тестов из этого
плана проходят без ослабления допусков**.

**2. Backoff при неудачном CAS** — SKILL §5 намеренно не предписывает: голый
retry, `runtime.Gosched()` — на усмотрение исполнителя. Не переусложнять ради
бенчмарка ценой читаемости (SKILL §6: цель — честное сравнение).

### Тесты — какие свойства обязаны быть покрыты

Файл `internal/limiter/lockfree_tokenbucket_test.go`. `fakeClock` уже есть в
`internal/limiter/clock_test.go` — потокобезопасный, переиспользовать, не
заводить свой. Свойства (не готовые тела — форму выбирает исполнитель;
образцы соседей: `tokenbucket_test.go`, `leakybucket_test.go`):

1. **Корректность на fake-clock, детерминированно, без `Sleep`:** полный бакет
   отдаёт ровно `capacity` подряд и денаит следующий; при нулевом `elapsed`
   пустой бакет денаит; `Advance`, дающий ровно K токенов, разрешает ровно K;
   долгий простой клампится по `capacity`; неудачный `AllowN` не списывает
   ничего; дробный refill накапливается между вызовами.
2. **`AllowN(0)` / `AllowN(-1)` → `true` без изменения состояния, включая
   метку времени** — аналог `TestTokenBucket_AllowNNonPositiveKeepsRefillTimestamp`:
   ловить именно то, что полурефилл между вызовами не теряется и не
   двоится.
3. **Дрейф float64 — обязательный кейс с не-двоично-точным шагом**, образец —
   `TestLeakyBucket_SteadyStateNonBinaryExactStep` (rate 1/с, шаг 100 мс,
   точное равенство допусков, не `>=`). Табличные кейсы с двоично-точными
   шагами этот дефект не ловят вообще — кейс нужен отдельным тестом. Учесть,
   что при «денай без CAS» остаток копится реже, чем у baseline, — тест всё
   равно обязан требовать точное число допусков.
4. **Stress-тест на гонки — центральный артефакт этапа** (паттерн — SKILL §4):
   замороженное время (refill=0), много горутин × много вызовов, инвариант
   «суммарно разрешённых ≤ `capacity`»; при `goroutines*callsPer > capacity`
   проверять точное равенство `capacity`, как в
   `TestTokenBucket_ConcurrentNoOverAdmit` (недобор при замороженном времени —
   тоже дефект). Превышение = гонка/потерянное обновление.
5. **Конкурентный прогон с движущимся временем** — аналог
   `TestLeakyBucket_ConcurrentWithLeak`: замороженный тест никогда не гоняет
   ветку с ненулевым refill под конкуренцией. Инвариант — верхняя граница
   `capacity + rate*прошедшее время` (с запасом на дробность).

**Счётчики в конкурентных тестах — только `atomic.Int64` с `Add(1)` на каждый
допуск.** Запрещены и `int` под mutex, и «локальный счётчик + один слив после
цикла»: contention на общем состоянии — предмет измерения, локальное
накопление снимает именно его (SKILL §5, PR #7). Опционально —
`testing/quick`-property, но это не гейт.

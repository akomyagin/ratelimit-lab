## Что делается в `stage-6/fast-lockfree`

Применение находок исследования к коду. План — [`stage-6-fast-lockfree.md`](stage-6-fast-lockfree.md),
он конкретен и самодостаточен: имена, сигнатуры, раскладка полей, форма
CAS-петли, поимённый список тестов, правки в бенчмарки и `cmd/bench`.

### Три решения приняты пользователем — не переоткрывать

1. **Пятая реализация добавляется рядом; существующая `LockFreeTokenBucket`
   остаётся нетронутой.** Её проигрыш втрое — задокументированный результат
   Этапа 5 и содержание README, он должен сохраниться как точка сравнения
   «наивный CAS». Правило «заменяй содержимое файла, не плоди `*_v2.go`» здесь
   сознательно не применяется: это третья точка сравнения, а не новая версия.
2. **Порт `Clock` не меняется.** Добавляется опциональный `SinceClock` рядом,
   выбираемый type assertion в конструкторе, с деградацией к `Now()`.
3. **`admitEpsilon` остаётся, но становится относительным** — снимает
   документированный потолок 2^24, поведение на текущих лимитах не меняет.

### Почему именно эти правки

Замерено основной сессией (i7-11700, 16 логических ядер, `parallel-16`, один
разделяемый лимитер, средние `-count=5`, один бинарь):

| Реализация | нс/оп |
|---|---|
| CAS + `atomic.Pointer` на снапшот (текущая) | 1460.4 |
| состояние в одном `atomic.Int64`, часы внутри петли | 1132.2 |
| то же, часы один раз до петли | 628.0 |
| то же + вынос констант из петли + падинг 128 Б | **194.6** |
| `sync.Mutex` token bucket | 466.8 |

Главный вывод исследования: «отрицательный результат» Этапа 5 — следствие
раскладки памяти, а не природы lock-free подхода. Подробности и оговорки —
`docs/RESEARCH.md` §1.3.

## Где остановились и что дальше по пайплайну

Пройдено: планирование (Fable) → гейт утверждения направления основной
сессией → кодинг (Opus, по плану).

Осталось:

1. **Проверка — два субагента параллельно.** Тестирование (`sonnet`): полнота
   покрытия под изменение плюс реальный прогон с сырым выводом. Независимое
   ревью (`opus`): свежий взгляд, промпт **на полноту, а не на фильтрацию** —
   «сообщи всё, что нашёл, с уверенностью и критичностью», отсев делает
   основная сессия. Не сливать в одного агента.
2. **Триаж находок — основная сессия.** Сначала проверить каждую по
   `file:line`, потом чинить. Отчётам на веру не верить.
3. **Финальный зелёный прогон — самому:**
   `go build ./... && go vet ./... && gofmt -l . && go test -race ./...`,
   плюс `GOMAXPROCS=4 go test -race -count=5 -run NoOverAdmit ./internal/limiter/`.
4. **Актуализация доков.** `README.md` (появилась пятая реализация и флаг
   `-algo=atomic`), `docs/TECHNICAL_PLAN.md` (раздел Этапа 6), `CLAUDE.md`
   (таблица файлов), `docs/POST_MVP_PLAN.md` §4а — часть техдолга закрыта:
   счётчик итераций CAS-петли не нужен, колонка `allocs/op` уже точно равна
   числу попыток (`docs/research/c1-benchmarking.md`).
5. **Commit, push, PR** — только в основной сессии, subject по-русски,
   трейлер `Co-Authored-By: Claude`.

## Ловушки, оплаченные этой сессией

- **Числа lock-free между сборками несравнимы**: один исходник давал 591…976 нс
  в шести бинарях при разбросе внутри прогона <5%. В README сравнивать только
  строки одного прогона; конкретные наносекунды из этого документа в доки не
  переносить.
- **Разрешающая способность стенда ~10%**: A/A-тест идентичного кода дал 6
  «значимых» различий из 8. Различия меньше 10% не доказаны.
- **Сломанный CAS выглядит правдоподобно и ускоряет бенчмарк.** Я сам написал
  `CompareAndSwap(x.Load(), next)` вместо сравнения с прочитанным `old`; такой
  CAS почти всегда проходит и занижает стоимость. Ловится только тестом на
  инвариант. Кандидат в `SKILL.md §5`.
- **Наивный микробенчмарк часов врёт.** Нужна базовая линия пустой петли:
  `time.Since` — 73.1 нс, `time.Now()` — ~115 нс (читает и стенные, и
  монотонные часы), а вся самая быстрая реализация — 92.5 нс.
- **Пометки `[из отчёта]` в `docs/RESEARCH.md` — гипотезы**, а не факты:
  полные тексты ячеек A1–A4 и B1 утрачены при перезагрузке машины, остались
  саммари. Перед переносом в код перепроверять по первоисточнику.

## Что осталось за рамками и почему

`docs/RESEARCH.md` §9.2 содержит приоритизированный список. Сознательно **не**
делается: distributed/Redis (меняет тему проекта с внутрипроцессной
конкурентности на эксплуатацию стора), пара `Reserve`/`Commit` в порту (у
lock-free версии парный commit добавит второй CAS-цикл и разрушит предмет
измерения), «починка» приближённости sliding window (Cloudflare публикует для
той же схемы 0,003% неверных решений при нуле ложных срабатываний).

Рекомендованные к установке скилы — `docs/RESEARCH.md` §5.

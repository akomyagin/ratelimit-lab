## 1. Что это

`ratelimit-lab` — учебная **библиотека rate limiting на Go** плюс честный
**бенчмарк-сьют**. В библиотеке три классических алгоритма ограничения частоты —
**token bucket**, **sliding window**, **leaky bucket** — реализованные для
одного процесса (single-process, in-memory), и отдельный CAS-based **lock-free**
вариант token bucket. Бенчмарк-сьют сравнивает их throughput и latency под
конкурентной нагрузкой.

Все реализации отвечают одному контракту (`limiter.Limiter`: `Allow() bool` и
батч-форма `AllowN(n int) bool`), безопасны для конкурентного использования из
множества горутин и не зависят от внешней инфраструктуры — это чистая библиотека
стандартной библиотеки Go.

Это **не сервис** и **не SaaS**: ни сервера, ни хостинга, ни сети. Единственный
исполняемый артефакт помимо самой библиотеки — CLI `cmd/bench`, который гоняет
лимитеры под нагрузкой и печатает сравнительную таблицу.

## 2. Зачем (и почему именно так)

Проект — **соло pet-проект интроверта с приоритетом обучения Go и конкурентности**.
Реализация ведётся AI-ассистентом по фиксированному пайплайну (см. `CLAUDE.md`).
Это не бизнес: экономическая целесообразность, монетизация и дистрибуция не
оцениваются и не важны. Метрика успеха — искренняя техническая сложность и то,
что автор разобрался в конкурентных примитивах на практике.

Учебная тема, ради которой проект и существует:

- **Конкурентные примитивы** — atomic vs mutex vs lock-free CAS-циклы
  (compare-and-swap). Три «простых» алгоритма дают baseline на mutex; четвёртый
  (lock-free token bucket) — это уже реальный конкурентный код, а не обёртка
  вокруг `time.Ticker`.
- **Алгоритмическая корректность под нагрузкой.** Легко написать лимитер,
  который «работает» на одном потоке, но пропускает больше лимита при
  конкурентном доступе (потерянные обновления, ABA-подобные эффекты). Ловим это
  отдельными stress-тестами.

## 3. Главная техническая мина (осознаётся заранее)

Lock-free CAS-based token bucket может быть **«менее корректным», чем кажется**.
Поэтому lock-free вариант — не просто «ещё одна реализация», а центральная точка
проекта: под него пишется отдельный **stress-тест на гонки** (много горутин
одновременно бьют по лимитеру; проверяем, что суммарное число пропущенных
запросов **не превышает** лимит), и весь пакет гоняется под `go test -race`.

## 4. Верхнеуровневая архитектура

```
internal/limiter/         # ядро-библиотека (Limiter + реализации)
├── limiter.go            # порт Limiter (Allow/AllowN) + Clock-абстракция
├── tokenbucket.go        # mutex-based token bucket (baseline)
├── slidingwindow.go      # sliding window
├── leakybucket.go        # leaky bucket (leak-as-a-meter)
└── lockfree_tokenbucket.go # CAS-based lock-free token bucket (Этап 4)
cmd/bench/main.go         # CLI-харнесс: нагрузка + сравнительный отчёт
```

Один общий контракт `Limiter` за портом; каждый алгоритм — отдельный файл-адаптер.
Время спрятано за абстракцией `Clock`, чтобы корректность тестировалась
детерминированно (fake-clock), а не через `time.Sleep`. Подробности — в
[`TECHNICAL_PLAN.md`](./TECHNICAL_PLAN.md).

## 5. Этапы (одной строкой; детали — TECHNICAL_PLAN)

- **Этап 0 — Бутстрап.** `go mod init`, скелет пакета `internal/limiter` с портом
  `Limiter` и заглушками трёх реализаций, заглушка `cmd/bench`, вся документация,
  SKILL. `go build`/`go vet` проходят чисто. *(этот этап)*
- **Этап 1 — Token bucket + база тестов.** Mutex-based token bucket, fake-clock,
  table-driven тесты корректности, первый `-race`-прогон.
- **Этап 2 — Sliding window.** Реализация + тесты; фиксируем поведение на границе
  окна (то, чем sliding отличается от fixed-window).
- **Этап 3 — Leaky bucket.** Leak-as-a-meter (без фоновой горутины) + тесты.
- **Этап 4 — Lock-free token bucket + stress-тесты гонок.** CAS-цикл на
  `atomic`, stress-тест «сумма пропущенных ≤ лимита», обязательный `-race`.
- **Этап 5 — Бенчмарк-сьют + отчёт.** `testing.B`-бенчмарки, CLI `cmd/bench`,
  сравнительная таблица throughput/latency, README с результатами.

## 6. После MVP

Осознанно вне MVP v1 — distributed rate limiting (Redis-backed), generic-бэкенд
под любой стор, blocking/`Wait`-семантика. Полный список и обоснование границы —
в [`POST_MVP_PLAN.md`](./POST_MVP_PLAN.md).

## 7. Не-цели MVP (осознанные границы)

- **Никакого distributed-варианта.** Только single-process, in-memory. Redis-
  backed rate limiting и любой сетевой стор — полностью вне v1.
- **Никакой инфраструктуры.** Ни Docker, ни Compose, ни сервера, ни БД
  (обоснование — `TECHNICAL_PLAN.md §Docker`).
- **Не блокирующий API.** `Allow()` возвращает решение немедленно; `Wait()`/
  блокировка до появления ёмкости — post-MVP.

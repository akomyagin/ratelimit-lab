# POST_MVP_PLAN — за пределами MVP `ratelimit-lab`

> Что **сознательно вынесено за пределы MVP v1** и в каком порядке имеет смысл
> добавлять потом. MVP — три single-process алгоритма + lock-free token bucket +
> stress-тесты + бенчмарк-сьют (см. [`PLAN.md`](./PLAN.md),
> [`TECHNICAL_PLAN.md`](./TECHNICAL_PLAN.md)).

---

## 1. Что осознанно вне MVP (границы v1)

Эти вещи **исключены из v1 намеренно**, чтобы MVP остался компактным и сфокусиро-
ванным на учебной цели (конкурентные примитивы в одном процессе):

- **Distributed rate limiting.** Никакого сетевого/разделяемого стора. Только
  in-memory single-process. Это главная отрезанная ветка — обоснование ниже (§2).
- **Blocking / `Wait`-семантика.** `Allow()` в MVP возвращает решение немедленно.
  Блокировка вызова до появления ёмкости (аналог `rate.Limiter.Wait`) — потом.
- **Публичный API (`pkg/`).** В MVP ядро в `internal/` (импорт извне запрещён).
  Вынос в `pkg/` со стабилизацией контракта — только при реальном спросе.
- **Конфиг/сериализация лимитов, метрики, наблюдаемость.** Для учебного бенчмарка
  не нужны; добавлять только если проект перерастёт в переиспользуемый компонент.

## 2. Distributed-вариант (Redis-backed) — почему потом, не сейчас

Distributed rate limiting (лимит, разделяемый между несколькими процессами/узлами
через общий стор) — **самая заметная и самая осознанно отрезанная** фича.

Почему вне MVP:

- Меняет тему проекта. MVP про **конкурентность внутри процесса** (atomic/mutex/
  CAS). Distributed — это уже про **сетевую атомарность** (Lua-скрипты в Redis,
  round-trip latency, частичные отказы стора) — другой класс сложности и другой
  учебный фокус.
- Тянет инфраструктуру (Redis) и ломает принцип «нулевых зависимостей и $0» —
  именно поэтому в MVP нет и Docker/Compose (`TECHNICAL_PLAN.md §8`).

Как добавлять, если возьмёмся:

- Ввести generic-порт стора (см. §3), реализовать Redis-адаптер (token bucket
  через атомарный Lua-скрипт: read-decide-write одной операцией на стороне Redis).
- Тогда — и только тогда — завести `docker-compose.yml` с Redis как dev-
  зависимостью и интеграционные тесты против реального Redis.

## 3. Generic-интерфейс под любой backend

Обобщить `Limiter` так, чтобы состояние жило за абстрактным стором (in-memory,
Redis, что угодно), а алгоритм не знал, где хранятся токены/окно. Это
предпосылка distributed-варианта и заодно чистое упражнение на дизайн API.
Риск — преждевременное обобщение: делать только когда появится **второй реальный
backend** (Redis), а не «на будущее».

## 4. Возможные дальнейшие направления (набросок, приоритет ниже)

- **GCRA** (generic cell rate algorithm) — четвёртый «настоящий» алгоритм,
  элегантная альтернатива token bucket; хорошая пара к бенчмаркам.
- **`Wait(ctx)`-семантика** поверх существующих лимитеров (блокировка до ёмкости,
  с отменой по контексту).
- **Расширение бенчмарк-отчёта** — графики latency-перцентилей (p50/p99), профиль
  под разным числом горутин, сравнение с `golang.org/x/time/rate` как эталоном.
- **Fuzz/property-based** проверки инварианта «≤ лимита» (`testing/quick` →
  полноценный fuzzing) поверх stress-тестов Этапа 4.

## 5. Что остаётся не-целью даже после MVP

- Не сервис/не демон: `ratelimit-lab` — библиотека + бенчмарк-харнесс, не
  запускаемый долгоживущий сервер.
- Не бизнес: монетизация/дистрибуция не рассматриваются ни на каком этапе.

> Детальный стек, архитектурные решения и разбивка по **пронумерованным Этапам**.
> Видение верхнего уровня — в [`PLAN.md`](./PLAN.md); что вне MVP —
> [`POST_MVP_PLAN.md`](./POST_MVP_PLAN.md).

---

## 1. Стек

- **Язык:** Go 1.23 (тулчейн в `~/sdk/go/bin`).
- **Зависимости:** только стандартная библиотека. Ядро — `sync`, `sync/atomic`,
  `time`; тесты — `testing`, `testing/quick`; бенчмарки — `testing.B`. Внешних
  модулей нет и без веской причины не добавляем (учебная цель — понять примитивы,
  а не собрать граф зависимостей).
- **Артефакты:** библиотека `internal/limiter` + CLI `cmd/bench`.

## 2. Структура: `internal/` + `cmd/`, почему нет `pkg/`

- Всё ядро — в `internal/limiter/`, чтобы компилятор **запрещал** внешний импорт:
  на этапе MVP это учебное приложение, а не публикуемая библиотека. Когда/если
  API стабилизируется и появится реальный спрос на импорт извне — вынести в
  `pkg/` (это отмечено в `POST_MVP_PLAN.md`), не раньше.
- `cmd/bench/main.go` — **тонкий** CLI-харнесс: парсинг флагов, запуск нагрузки,
  рендер таблицы. Никакой алгоритмической логики в `main` — только оркестрация
  над `internal/limiter`.
- **По файлу на алгоритм** в `internal/limiter/` (`tokenbucket.go`,
  `slidingwindow.go`, `leakybucket.go`, `lockfree_tokenbucket.go`); сам порт и
  общие абстракции (`Limiter`, `Clock`) — в `limiter.go`.
- Каждая заглушка из Этапа 0 помечена `TODO(Этап N)`; при реализации **заменяем
  содержимое файла**, а не плодим параллельные `*_v2.go`.

## 3. Центральный контракт: порт `Limiter`

Все алгоритмы прячутся за одним интерфейсом (ports & adapters):

```go
type Limiter interface {
    Allow() bool        // одно решение, без блокировки
    AllowN(n int) bool  // батч из n единиц за один вызов
}
```

Инвариант, общий для всех реализаций: **безопасность для конкурентного
использования из множества горутин**. Реализация, корректная только на одном
потоке, — это баг, а не «вариант». Компилятор держит контракт через
`var _ Limiter = (*T)(nil)` в каждом файле (эти assertions заведены уже в Этапе 0
поверх заглушек, чтобы интерфейс не «уплыл» незаметно).

## 4. Абстракция времени: `Clock`

Все лимитеры зависят от времени (refill, leak, окно). Прямой вызов `time.Now()`
внутри сделал бы тесты корректности недетерминированными (пришлось бы `Sleep`).
Поэтому время спрятано за портом `Clock` (`Now() time.Time`):

- Прод-конструкторы получают `SystemClock` (обёртка над `time.Now`).
- Тесты инжектят **управляемый fake-clock** и «прокручивают» время вручную —
  корректность проверяется мгновенно и детерминированно.

Fake-clock появляется в Этапе 1 вместе с первым алгоритмом (в `internal/limiter`,
в `_test.go` или в маленьком тест-хелпере) и переиспользуется всеми последующими.

## 5. Ключевые алгоритмические решения

- **Token bucket (Этап 1):** непрерывный refill как арифметика по прошедшему
  времени (`elapsed * rate`), без фоновой горутины-тикера. Baseline — под
  `sync.Mutex`.
- **Sliding window (Этап 2):** решаем и **фиксируем в этом документе** при
  реализации — sliding-window-log (точный, память O(запросов в окне)) или
  weighted sliding-window-counter (аппроксимация двух fixed-окон, память O(1)).
  Дефолт — weighted counter как более практичный; лог — если нужна точность.
- **Leaky bucket (Этап 3):** leak-as-a-meter — уровень воды пересчитывается по
  прошедшему времени при каждом `Allow`, без отдельной сливающей горутины.
- **Lock-free token bucket (Этап 4):** состояние (кол-во токенов + метка времени)
  упаковано так, чтобы обновляться одним `atomic.CompareAndSwap` в CAS-цикле:
  прочитать состояние → вычислить новое → `CAS`; при неудаче — повтор. Это
  главный конкурентный код проекта. Здесь же — риск ABA/потерянных обновлений,
  под который пишется stress-тест (см. §6, Этап 4).

## 6. Разбивка по Этапам

### Этап 0 — Бутстрап *(этот этап)*
`go mod init github.com/akomyagin/ratelimit-lab`; скелет `internal/limiter` с
портом `Limiter` + `Clock` и заглушками `tokenbucket.go`/`slidingwindow.go`/
`leakybucket.go` (compile-time assertions на месте, тела — `panic`/`TODO(Этап N)`);
заглушка `cmd/bench/main.go`; PLAN/TECHNICAL_PLAN/POST_MVP_PLAN, README, CLAUDE.md,
SKILL. **Критерий готовности:** `go build ./...` и `go vet ./...` проходят чисто.

### Этап 1 — Token bucket + база тестов
Mutex-based `TokenBucket` (конструктор с `rate`, `capacity`, `Clock`); refill-
математика. Fake-clock. Table-driven тесты корректности (пустой/полный бакет,
refill во времени, `AllowN`). Первый прогон `go test -race ./...`. **Готово:**
детерминированные тесты зелёные под `-race`.

### Этап 2 — Sliding window
`SlidingWindow` (выбранный вариант — см. §5, решение зафиксировать здесь при
реализации). Тесты, отдельно — поведение на **границе окна** (то, чем sliding
лучше наивного fixed-window: нет всплеска 2×limit на стыке). **Готово:** тест
границы окна зелёный.

### Этап 3 — Leaky bucket
`LeakyBucket` (leak-as-a-meter). Тесты: сглаживание всплеска в постоянный отток,
переполнение при полном бакете. **Готово:** тесты steady-state и переполнения
зелёные.

### Этап 4 — Lock-free token bucket + stress-тесты гонок
`LockFreeTokenBucket` на `sync/atomic` (CAS-цикл, упакованное состояние).
**Stress-тест на гонки** — центральный артефакт этапа: N горутин параллельно
вызывают `Allow`, счётчик разрешённых атомарный; проверяем **суммарно
пропущенных ≤ теоретического лимита** за окно. Весь пакет — обязательно под
`go test -race`, желательно с `-count` и `GOMAXPROCS>1`. Опционально — быстрый
контроль корректности через `testing/quick`. **Готово:** stress-тест стабильно
зелёный под `-race`, инвариант «≤ лимита» не нарушается.

### Этап 5 — Бенчмарк-сьют + сравнительный отчёт
`testing.B`-микробенчмарки на каждый лимитер (`b.RunParallel` для конкурентного
профиля). CLI `cmd/bench`: флаги `-algo`, `-goroutines`, `-rate`, `-duration`;
драйвер нагрузки; рендер сравнительной таблицы throughput/latency. README
дополняется реальными результатами (mutex vs lock-free — что дал CAS и чего
стоил). **Готово:** `go test -bench` и `cmd/bench` дают воспроизводимую таблицу,
README обновлён.

## 7. Тестирование (сводка; детали — SKILL.md §4)

- Корректность — table-driven тесты с fake-clock, детерминированно, без `Sleep`.
- Гонки — stress-тесты с большим числом горутин + **обязательный `-race`** на
  весь пакет (не только на lock-free — mutex-версии тоже прогоняются под гонки).
- Производительность — `testing.B` + `b.RunParallel`; `cmd/bench` — человеко-
  ориентированный сравнительный харнесс поверх тех же лимитеров.
- CI-эквивалент локально: `go build ./... && go vet ./... && go test -race ./...`.

## 8. Docker Compose — решение: НЕ заводим

`ratelimit-lab` — **чистая библиотека без сервиса, БД и внешних
контейнеризируемых зависимостей**. Всё состояние — в памяти процесса; сети нет;
единственный бинарник (`cmd/bench`) гоняет нагрузку локально и печатает таблицу.
Контейнеризировать нечего, поэтому `docker-compose.yml` не даёт никакой ценности
и **в проект не заводится**.

Отличие от других pet-проектов портфеля, где compose есть (например для dev-
зависимости вроде локального Redis/ollama): здесь аналога нет — весь смысл MVP
именно в single-process-конкурентности без внешних сторов. Redis появился бы
только вместе с distributed-вариантом, а он **осознанно вынесен в
`POST_MVP_PLAN.md`**. Если этот вариант когда-нибудь начнут делать, тогда и
пересмотреть решение по Docker — не раньше.

**Итог:** Docker/Compose в проекте нет и не планируется.
